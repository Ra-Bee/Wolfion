# Wolfion deployment

**Pipeline:** push to `main` on github.com/Ra-Bee/Wolfion → Vercel auto-builds → wolfion.website (API on Render). No other deploy trigger.

**The agent is hard-blocked from all writing git operations** (push, fetch, merge, commit — even `git fetch`, which writes pack objects). Read-only git works with `--no-optional-locks`. Only the **user** can deploy, by running `deploy.sh` in their Shell (their shell is not blocked).
**Why:** token delivery via chat/secure-box kept failing (chat turns the paste into a secret-name chip; the secure box auto-fills a stale token). A terminal `read` prompt is the only clean channel.

**Token:** a classic PAT with `repo` scope, or a fine-grained PAT with Contents read **and write** (fine-grained default is read-only → 403 on push). `deploy.sh` probes auth + a no-commit PUT before pushing (200 auth, 422 = write OK, 403 = no write, 401 = invalid).

## deploy.sh must deploy a clean-root squash of the WORKING TREE
- Push a single squashed root commit of the on-disk tree via `git write-tree` + `git commit-tree` (no parents), then force-push to `main`. Set `GIT_AUTHOR_*`/`GIT_COMMITTER_*` or `commit-tree` errors on empty ident.
- **Snapshot the working tree, not HEAD** (`git add -A; TREE=$(git write-tree)`). Recoveries often live only in the working tree while HEAD points at an old commit, so deploying `HEAD^{tree}` would ship the wrong version.
- **Why clean-root:** a full-history force-push is blocked by GitHub secret scanning — old history contains a real Clerk `sk_test_` key in `.env.example` (GitHub mislabels it "Stripe Test API Secret Key"). The current tree is clean (placeholders only); a parent-less commit of just the current tree never exposes historical secrets, and Vercel only needs the latest files.

## Recovering lost work after a checkpoint rollback
A Replit rollback / "restore previous live site" can revert the working files to an OLD version (history is intact, working tree is not). **The finished overhaul = the last commit whose `wolfion-store.ts` still contains `computeShortSocksYarn`** (find via `git log --all -S computeShortSocksYarn -- <path>`). That commit already integrates both the overhaul and the electricity/rent/users-list/investments pages — no re-combine needed.
**Agent-safe recovery (no git writes):** `git --no-optional-locks archive <commit> -- artifacts/wolfion | tar -x` extracts that subtree over the working tree. Restore any api-server routes separately (they live outside artifacts/wolfion). Then typecheck wolfion + api-server.

## Google Play (Android via Capacitor) publishing
- **Permanent package name is `wolfion.aab`.** The Play app was created (by mistake) with package name `wolfion.aab`, and a Play package name is immutable. So `artifacts/wolfion/android/app/build.gradle` `applicationId` MUST stay `wolfion.aab` — do NOT "fix" it to `com.wolfion.app`. The code `namespace` can stay `com.wolfion.app` (applicationId ≠ namespace is fine). Symptom of mismatch: Play upload error "needs to have the package name wolfion.aab".
- **The "lost" upload key was recoverable — no key reset needed.** Google's expected upload cert SHA1 is `85:83:E1:BE:FE:E1:51:A1:D8:BC:73:A7:3D:F4:D3:87:28:3B:1F:97`. The matching keystore lives at `.local/state/keystore/upload-keystore.jks` (alias `upload`; password is a secret, not stored here — it was in the session transcript). Signing with it makes Play accept the .aab immediately. Do not generate a new upload key or request a Play key reset before checking this file.
- **CI build:** GitHub Actions workflow "Build Wolfion Android AAB" (`.github/workflows/wolfion-android-release.yml`) builds+signs the .aab from secrets `ANDROID_KEYSTORE_BASE64`, `ANDROID_STORE_PASSWORD`, `ANDROID_KEY_ALIAS` (=`upload`), `ANDROID_KEY_PASSWORD` (+ `VITE_*`). Trigger: `gh workflow run "Build Wolfion Android AAB" --ref main`; artifact name `wolfion-release-aab` (contains `app-release.aab`). Uses pnpm 10 + JDK 21.
- **GitHub token scope:** the PAT has `repo` only, NO `workflow` scope → workflow-YAML edits must be done by the user in the GitHub web UI; all other files can be committed programmatically via the Contents API (`gh api -X PUT repos/.../contents/<path>`).
- **Verify a built .aab before delivering:** package name via `unzip -p app-release.aab base/manifest/AndroidManifest.xml | strings | grep wolfion`; signature via `keytool -printcert -jarfile app-release.aab | grep SHA1` (expect `85:83:E1:BE…`). `present_asset` rejects `.aab`, so zip it first.

## App launcher icon + in-app Google login (Capacitor)
- **Icon comes from committed `android/app/src/main/res/mipmap-*` PNGs; `cap sync` does NOT regenerate them.** If the icon shows the default Capacitor blue-X, the mipmaps were never replaced. Generate ic_launcher/ic_launcher_round/ic_launcher_foreground at all densities with ImageMagick (`magick`) and set adaptive bg via `values/ic_launcher_background.xml` (color name `ic_launcher_background`). Brand: orange #FF5A00 bg + white WOLFION mark.
- **Mirror architecture means change type dictates deploy path:** web/UI changes (e.g. safe-area) ship via Vercel (GitHub push) and appear in the app instantly; native changes (icon, `capacitor.config.ts`) require an AAB rebuild + Play re-upload.
- **Slide-in menu panels need their own safe-area padding.** Layout headers having `safe-pt` is not enough — each `SheetHeader` (mobile menu, account menu, admin menu) also needs `safe-pt` or its top content sits under the status bar/notch.
- **Status-bar/camera overlap on Android 15/16 = enforced edge-to-edge; CSS `env(safe-area-inset-*)` is 0 in the mirror WebView, so a CSS-only fix does NOTHING.** The working fix is NATIVE in `MainActivity.onCreate`: pad the Capacitor WebView by `WindowInsetsCompat systemBars()|displayCutout()` insets (a View draws its background across padding, so set the WebView bg to the theme strip color — light `#FAFAFA` / dark `#050505`, keyed off `Configuration` night mode) and set `WindowInsetsControllerCompat` light/dark bar icon appearance. Needs an AAB rebuild (native). Caveat: strip color follows SYSTEM dark mode at onCreate, not the in-app theme toggle, so they can mismatch if the user forces a different in-app theme.
- **In-app Google OAuth workaround (best-effort, mirror app):** set capacitor `overrideUserAgent` to a plain Chrome-Android UA (drops the `wv` marker so Google's `disallowed_useragent` check passes) + `server.allowNavigation` limited to top-level redirect hosts only so the flow stays in-WebView and the session cookie lands there. **Google's chain also top-level hops through `accounts.youtube.com` (cookie sync) and sometimes `myaccount.google.com` — omitting them kicks the user to external Chrome stranded on a YouTube page** (real field bug, Jul 2026). Current list: wolfion.website, accounts.google.com, accounts.youtube.com, myaccount.google.com, *.clerk.accounts.dev. Sub-resources don't need listing; keep least-privilege (review flagged broad wildcards as attack-surface). **Why fragile:** Google may tighten webview detection anytime; can't test device OAuth here. Email/password still works if Google blocks. The robust alternative (custom-tab + deep-link + token handoff) conflicts with the cookie-based mirror app and is a bigger rearchitecture.
- **Native app polish:** pull-to-refresh (`pull-to-refresh.tsx`) sets sessionStorage `wolfion-skip-splash` before reload; the index.html native splash script skips+clears it, so the marble logo splash only shows on cold start. Auth screen (`auth-shell.tsx`) disables blob/halo animations and backdrop-filter on touch devices (WebView typing lag). Manifest has `windowSoftInputMode=adjustResize`.

## API hosting (July 30, 2026)
- wolfion.website `/api/*` rewrites to Render (`wolfion-api-fqmu.onrender.com`) per `artifacts/wolfion/vercel.json`. Sign-up depends on it; the rest of the app uses Firebase directly.
- `RENDER_API_KEY` secret works with api.render.com (service id srv-d888ndl7vvec738ingk0): check deploys, tail logs, trigger deploys with POST /services/{id}/deploys {"commitId":...}.
- Render deploys had SILENTLY failed since June (user only noticed via failure emails weeks later). Root cause: runtime Dockerfile `npm install firebase-admin` un-lockfiled — @firebase/database-compat started requiring @firebase/app → crash on boot. Fix: pin firebase-admin@13.10.0 AND install @firebase/app explicitly (artifacts/api-server/Dockerfile). Lesson: that npm install has no lockfile, so transitive upgrades can break boot at any time; test the exact install combo locally (`node -e "require('firebase-admin/database')"`) before pushing.
- Render auto-deploy on push can lag or skip; trigger manually via API when in a hurry.
